## はじめに

最近、選択・二値・スコアだけを返す「decision model」が増えてきました。Jev、Liquid AI の d1、Perplexity の Decider など、文章は生成せず「どれを選ぶか」「はい / いいえの確率」だけを返すモデルです。分類やルーティング、LLM-as-a-judge の代わりに安く速く使えるのが売りです。

decision model 向けのベンチマークとしては Jev Decision Index などがあるのですが、日本語のタスクがありません。日本語で使ったらどうなるのか気になったので、勉強がてらお試しで日本語のベンチマークを作ってみました。

結果の公開サイトはこちらです。

https://mst-ja-decision-bench.masseater.dev

コードはこちらです。

https://github.com/masseater/mst-ja-decision-bench

結果はサイトを見てもらうとして、この記事では作るときに工夫したところと、やってみて学んだことを書きます。あくまで勉強目的なので、厳密さよりも「一通り回す」ことを優先しています。

![概要ページ](/images/ja-decision-model-bench/top.png)

## 何を測ったか

タスクは 2 つです。

- **JNLI 含意関係**: JGLUE の JNLI valid 2,434 件。2 文の関係を「含意・矛盾・中立」の 3 択で答えさせる。正解は人手ラベル
- **業務ルール判定**: 架空の会社 25 社分の社内規程と、それに対する事例 500 件。規程に適合しているかを二値で答えさせる。正解は Claude Opus 5.5 が付けたもの

JNLI は「素直な日本語の分類」、業務ルール判定は「日本語で decision model を業務に使うならこういう使い方をしそう」という想定で選びました。

## 工夫したところ

### 既存ベンチのやり方に寄せる

最初は自己流で採点していたのですが、途中で既存の decision model ベンチ(Jev Decision Index、S1MB、DecideBench、JevBench、Arize の比較、AIM-Decision)を読んで、なるべくそちらに寄せました。自分で考えるより、先にやっている人の判断に乗っかった方がだいたい正しいです。

取り入れたのは主に次の点です。

- 問題文は全モデルで同じにし、モデルごとにプロンプトを調整しない
- 未対応やエラーは 0 点として分母に入れ、答えられた割合は coverage として別に出す。失敗を分母から外すと「難しい問題だけ落とすモデル」が得をするため
- ランダムに答えたときを 0 にした skill に揃える。3 択と二値では偶然当たる確率が違うので、生の正解率のままだと比べられない
- NLI は正解率ではなく macro-F1 で採点する
- 確率から ECE と Brier を出し、確信度と実際の正解率のグラフ(キャリブレーション曲線)を描く
- 95% 信頼区間を付ける
- 費用と速度はスコアに混ぜず、別の軸で見せる

信頼区間を付けたのは実際に役に立ちました。最初は JNLI を 200 件だけ使っていたのですが、正解率 70% 付近だと区間が ±6 ポイントほどあって、モデルの差がほとんど見分けられませんでした。JNLI は人手ラベルがあって追加費用がかからないので、valid 全件に増やしています。

### 業務ルール判定は最小差分ペアで作る

業務ルール判定は自作のデータなので、一番手を入れたところです。

最初の版は「条文 1 つと事例 1 つ」を渡して判定させていたのですが、これだと条文を読まなくても話題語だけで当たってしまいます。そこで次のように作り直しました。

- テーマごとに、目的・定義・例外・他条の参照を含む 8〜12 条の規程を作り、毎回その規程全体を読ませる
- 事例は 2 つ以上の条を組み合わせないと判断できないものにする
- [DecideBench](https://github.com/choyiny/decidebench) に倣って、ほぼ同じ 2 つの事例の 1 か所(金額、日付、役職、手続きの順序、例外の条件)だけを変えて答えを逆にした「対」にする
- 対の両方に正解した割合を「対の正解率」として出す

対の正解率が効いていて、話題語に反応しているだけのモデルは片方しか当たらないので、ここが極端に低くなります。実際、span-01 系は対の正解率が 13.8% で、規程をほとんど読めていないことがはっきり出ました。

ほかにも細かい点として、

- 問いは「適合しているか」の肯定形に揃えた。Arize の比較で、否定形の問いが判定の逆転を招いていたため
- Clef 系は入力の先頭約 2,000 トークンしか読まないので、規程は 1,500 字以内に収めた
- 2 回目の生成では 1 回目の問いを渡して、同じ論点を繰り返さないようにした

あたりも気をつけています。

### 正解ラベルは 3 回聞いて、割れたものを分ける

業務ルール判定の正解は Opus 5.5(effort high)に付けさせています。1 問ごとに `claude -p` を構造化出力で 3 回独立に呼び、3 回とも一致したものだけを採点に使い、割れたものは hard として別集計にしました。

ただ、やってみると 500 件中で票が割れたのは 1 件だけで、hard の仕組みがほとんど機能しませんでした。LLM に同じ問題を何度聞いても、だいたい同じ答えが返ってきます。そこで「作るときに意図した答え(対の a が適合、b が不適合)と多数決が食い違う」問題も hard に入れるようにしました。

また、JNLI では Opus 5.5 にも 200 件だけラベルを付けさせて、人の正解との一致率(91.5%)を出しています。業務ルール判定のスコアは「Opus 5.5 との一致率」でしかないので、LLM ラベルがどのくらい外れるかの目安として載せています。

### Noul しか受け付けないモデルにも 3 択を解かせる

decision model には、選択式(Choice)に対応していて選択肢ごとの確率を返してくれるモデルと、span-01 系のように「はい / いいえ」(Noul)しか受け付けないモデルがあります。

Decision Index のルールだと未対応の形式は 0 点ですが、それだと span-01 系は JNLI で何も測れません。そこで、選択肢ごとに「次の答えは正しいですか: 含意」のような Noul の問いを作り、1 リクエストにまとめて送って「はい」の確率が最大の選択肢を答えにしました。1 件 1 呼び出しなので費用も他のモデルと揃います。

この方法はどの既存ベンチにも書かれていなかった独自のやり方なので、結果では `*` を付けて区別しています。

### モデルが数十に増えても成り立つようにする

decision model は OpenRouter 上の十数個がすべてではなく、他のプロバイダにもあり、今後も増えそうです。なので最初から「モデルが数十になっても破綻しない」ことを意識しました。

- モデルの呼び出しは当面 OpenRouter の SDK(`@openrouter/sdk` の `systemOne.create`)に一本化しつつ、モデルは `{ provider: "openrouter", id: "typesafe/jev-1.13" }` のように provider を含めて持ち、他のプロバイダを後から足せるようにした
- 応答は Effect の `PersistedCache` で 1 件 1 ファイルにキャッシュし、成功した判定は再実行しても呼び直さない。モデルを 1 つ足しても、そのモデルの分だけ呼べば済む
- 表はソートでき、既定は上位 10 件で「すべて表示」とモデル名での絞り込みを付けた。散布図はラベルの重なりを避けてホバーで名前を出し、グラフはタスクごとに別ページにして縦に積んだ

性質の違うタスクを 1 つの表に並べると平均値だけが独り歩きするので、タスクごとにページを分けて、両タスクの平均は「参考」として概要ページに置くだけにしています。

## やってみて学んだこと

### タスクによって順位はかなり変わる

JNLI のような素直な分類では上位のモデルがほぼ横並びなのに、規程を読ませる業務ルール判定では差が大きく開きました。JNLI で上位のモデルが業務ルールでは中位に落ちたり、逆に JNLI では振るわなかったモデルが業務ルールでは上位に来たりもします。1 つのタスクの結果だけで「このモデルが強い」とは言えないので、自分の用途に近いタスクで測るのが大事だなと思いました。

### 確信度は当てにならないことがある

キャリブレーション曲線を描いてみると、確信度が上がっても正解率がほとんど上がらないモデルがありました。確率を返してくれるからといって、そのまま閾値に使ってよいとは限りません。正解率だけでなく、確信度と実際の正解率のずれも見ておくべきだと分かりました。

### 有料版と無料版が同じものを返していた

有料の span-01 と無料の span-01 lite は、全 2,934 問で答えも確率も完全に一致しました。少なくとも OpenRouter 経由で日本語を投げた範囲では、同じものが返ってきているように見えます。並べて測ってみないと気づかないことでした。

### 費用は実測から見積もり、上限をかけておく

新しいモデルを回す前に、実測済みのモデルのトークン数と単価から見積を出してから回すようにしていました。OpenRouter 上の新規 14 モデルを全件回したときは、見積 $1.74 に対して実費は約 $0.96 でした。全モデル合わせても 1 周 1 ドル前後なので、decision model のベンチは安く回せます。

とはいえ AI エージェントに回させていると何かの拍子に呼びすぎるのが怖いので、OpenRouter の API キーには月の利用上限をかけています。Opus 5.5 でのラベル付けは API 換算だと 30 ドルを超えますが、サブスクリプション経由の `claude -p` で動かしたので実際の請求はありません。

ハマったところとしては、OpenRouter の `:free` 付きのモデルがアカウントのデータポリシー設定で拒否されることがありました。有料版でも全件で数セントなので、有料版を使っています。

### 遅いモデルは本当に遅い

ほとんどのモデルは 1 判定 200〜500 ms 程度なのですが、Solar Decide は業務ルール判定で p50 が約 18.7 秒、p95 が約 29 秒と桁違いでした。精度は上位なのですが、500 件回すだけでも待たされます。速度を別の軸で見せておいてよかったところです。

### decision model を lint にも使ってみた

このリポジトリでは、jev-lint という decision model でコード規約を判定するツールを CI に入れています。最初は無料の span-01 lite で判定していたのですが、UI 状態を持たない純粋関数を「UI 状態の扱いの規約違反」と誤検知して CI が落ちました。

span-01 lite に違反例と違反でない例を判定させてみると、両者をほとんど区別できていませんでした。そこで、そのルールの判定だけを今回のベンチで 1 位だった Decider に切り替えています。lint の設定を緩めるのではなく判定するモデルを替えて直せたので、ベンチの結果が早速役に立ちました。

## おわりに

勉強目的のお試しでしたが、作ってみると「データの作り方」と「採点のルール」で結果の意味がかなり変わることを実感しました。特に、最小差分ペアと coverage の扱いは、既存ベンチを読まなければ思いつかなかったと思います。

decision model は 1 判定あたりの費用が非常に安いので、手元のユースケースに近いタスクを作って測ってみるのはおすすめです。今後は OpenRouter 以外のプロバイダの decision model も足していきたいと思っています。
