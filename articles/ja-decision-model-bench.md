選択・二値・スコアだけを返す「decision model」を、日本語のタスクで測るベンチマークを勉強がてら作りました。

結果の公開サイトはこちらです。

コードはこちらです。

https://github.com/masseater/mst-ja-decision-bench

結果と作り方はサイトとリポジトリを見てもらうとして、この記事では、なぜ作ることにしたのか、作りながら何をどう判断したのか、その判断がどこに行き着いたのかを書きます。ベンチマークを作るのは初めてで、最初の見立てが外れて途中で引き返したところが何か所もあります。その引き返した理由が、この記事でいちばん書きたいことです。

## 作ったきっかけ

decision model は、文章を生成せずに「どれを選ぶか」「はい / いいえの確率」だけを返すモデルです。2026 年 9 月 15 日に [TypeSafe](https://typesafe.ai) が [Jev](https://typesafe.ai/blog/introducing-system-one-models-and-jev) をリリースしてから世界的なブームになり、各社が色んなモデルを出しています。

自分はタイムラインや友人がワイワイしているのを見て数日遅れで使い始めたのですが、使ってみてめちゃくちゃ革命を感じました。その革命に感動し、とりあえず [Claude Code](https://code.claude.com/docs) のハーネスに Jev を組み込み始めました。[jev-lint](https://github.com/mizchi/jev-lint)、[jev-pruner](https://github.com/tamaratran/jev-pruner)、[fast-jev-compaction](https://github.com/tamaratran/fast-jev-compaction)、[jevgrep](https://github.com/dzhng/jevgrep) などを入れたり、自作の [cc-jev-teacher](https://github.com/masseater/cc-jev-teacher) を作ったりしています。

その中で、

- Jev は超激安だと分かってはいたものの、従量課金を使うのは心理的なハードルがあった
- そこで無料で使える [span-01 lite](https://openrouter.ai/respan/span-01-lite) で判定させていたら、Jev のときより明らかに誤検知が増えた
- 日本語での性能がどれくらい違うのかを知りたくて、日本語のベンチマークを探しに行った
- [Jev Decision Index](https://huggingface.co/spaces/multimodalart/jev-decision-index) など、decision model 向けのベンチマークはあるが、日本語のタスクがない
- 日本語でいくつかのモデルを比較してみたものはあるが、現時点の decision model をまとめて体系的に測ったものは見つからなかった

となりました。
なければ作ってみよう、ということで、勉強がてら作ってみました。

## 何を測りたかったのか

きっかけが lint の誤検知だったので、測りたかったのは「日本語で書いたルールに照らして、目の前のものを正しく判定できるか」です。既存のベンチにある分類やルーティングの精度ではなく、自分がハーネスで decision model にやらせていることそのものを測りたいと思いました。

ただ、自分の用途に寄せたタスクだけだと、他の人が見たときに比べる基準がありません。そこで、日本語の NLP で定番の [JNLI](https://github.com/yahoojapan/JGLUE)(2 文の関係を「含意・矛盾・中立」の 3 択で答える)を基準として置き、その横に自分の用途に近い自作タスクを並べることにしました。JNLI は人が付けた正解があるので、正解を自分で用意する手間がかからないのも決め手でした。

自作タスクは「業務ルール判定」と呼んでいます。架空の会社の社内規程を読ませて、ある事例がその規程に適合しているかを「はい / いいえ」で答えさせるものです。社内規程を選んだのは、lint のルールと同じで「自然文で書かれた決まりに照らして判定する」形だからです。

## 途中で引き返したこと

### 200 件で十分だと思っていた

最初はお試しなので、JNLI は 200 件でいいと思っていました。ところが結果に 95% 信頼区間を付けてみると、正解率 70% 付近で ±6 ポイントほどの幅があり、モデル同士の差がほとんど区間の中に埋もれてしまいました。順位表のようなものは出るのに、その順位にはほぼ意味がない状態です。

JNLI は人手の正解があり、件数を増やしても正解を付ける費用がかかりません。なので valid の 2,434 件を全部使うことにしました。区間を付けていなかったら、200 件の順位をそのまま信じていたと思います。

### 自作タスクは「それっぽい数字」が出ていた

業務ルール判定の最初の版は「条文 1 つと事例 1 つ」を渡す形でした。一応それっぽい結果は出たのですが、見返すと「第 n 条」は飾りで、条文を読まなくても事例の話題語だけで当てられる問題ばかりでした。これでは「日本語の規程を読めているか」ではなく「話題語に反応できるか」を測っていることになります。

ここで一度、既存の decision model ベンチ(Jev Decision Index、[S1MB](https://github.com/hotchpotch/S1MB)、[DecideBench](https://github.com/choyiny/decidebench)、[JevBench](https://github.com/fstandhartinger/jevbench)、[Arize の比較](https://arize.com/blog/decision-model-benchmark/)、[AIM-Decision](https://aimultiple.com/system-one))をちゃんと読みました。規程全体に対する適合判定はどこにもなかったのですが、DecideBench の「ほぼ同じ 2 つの事例の 1 か所だけを変えて答えを逆にした対にする」という作り方が、まさに話題語への反応を潰すためのものだったので、これを取り入れて作り直しました。規程は 1 テーマにつき 8〜12 条にして毎回全体を読ませ、事例は 2 つ以上の条を組み合わせないと判断できないものにしています。

作り直す前後で同じモデル(span-01 lite)を測ると、skill は 40.9 から 12.2 に落ちました。作り直す前の数字は、規程を読む力ではなく話題語への反応を測っていたということです。自作タスクは、それっぽい数字が出ても何を測っているのかを疑った方がいい、というのがここでの学びでした。

### LLM に 3 回聞いても割れない

業務ルール判定の正解は [Claude Opus 5.5](https://www.anthropic.com/claude/opus)(effort high)に付けさせています。本来は人がチェックすべきですが、流石に 500 件は嫌だったので、1 問ごとに `claude -p` を構造化出力で 3 回独立に呼び、3 回とも一致したものだけを採点に使い、割れたものは「hard」として別にするつもりでした。

ところが実際に回してみると、票が割れたのは 1 件だけでした。同じ問題を何度聞いても、LLM はだいたい同じ答えを返してきます。3 回聞けば迷う問題が見つかるだろうという見立ては外れました。結局、「作るときに意図した答えと多数決が食い違う問題」も hard に入れることにしました。

このやり方の限界は自覚しています。業務ルール判定のスコアは「Opus 5.5 との一致率」でしかありません。[Opus の日本語性能はかなりトップクラス](https://nejumi.ai)(Nejumi LLM リーダーボードでは前世代の Opus 5 が首位)なので参考にはなると思いますが、JNLI で Opus 5.5 のラベルと人の正解を比べると一致率は 91.5% で、LLM のラベルも 1 割弱は人とずれます。あくまで個人が試しに作ってみた程度のものだということはご承知おきください。

### 自己流の採点をやめた

最初は正解率を出していただけでした。既存ベンチを読んで、自分が気にしていなかった点がいくつもあると分かりました。

- 答えられなかった問題を分母から外すと、難しい問題だけ落とすモデルが得をする。なので未対応やエラーは 0 点で分母に入れ、答えた割合は別に出す
- 3 択と二値では偶然当たる確率が違うので、生の正解率のままだとタスク間で比べられない。ランダムに答えたときを 0 にした値(skill)に揃える
- 費用と速度はスコアに混ぜず、別の軸で見せる

どれも言われてみればその通りなのですが、自分だけでは思いつきませんでした。自分で考えるより、先にやっている人の判断に乗った方がだいたい正しいです。採点はまるごと Jev Decision Index のやり方に揃えました。

一方で、どのベンチにも書かれていなかったこともありました。span-01 系のように「はい / いいえ」しか受け付けないモデルに、3 択の JNLI をどう解かせるかです。ルール通り未対応を 0 点にすると、JNLI では何も測れません。きっかけになった span-01 lite が測れないのでは意味がないので、選択肢ごとに「はい / いいえ」で聞いて確率が最大のものを答えにする、という独自のやり方をとりました。既存ベンチにない手順なので、結果では `*` を付けて区別しています。

## 費用との向き合い方

decision model は安いのですが、作業は Claude Code に任せて回していたので、何かの拍子に呼びすぎるのが怖かったです。そこで、新しいモデルを足すときは、先に少数のサンプルを実測してトークン数と単価から見積を出させ、自分が OK してから全件を回す、というルールを最初に決めました。推測の見積で回すとどこかで痛い目を見そうだったからです。

実際、承認前に呼んでしまった分が一度あり、そのキャッシュだけを残して以降は止めています。安いからこそ、気を抜くと際限なく回してしまうので、このルールは決めておいてよかったです。

## ベンチの結果が自分の道具選びに戻ってきた

最後に、作ってよかったと思えた話です。

このリポジトリ自身も jev-lint を CI に入れていて、最初は無料の span-01 lite で判定していました。あるとき、UI 状態を持たない純粋関数が「UI 状態の扱いの規約違反」と判定されて CI が落ちました。span-01 lite に違反例と違反でない例を判定させてみると、両者をほとんど区別できていません。まさに、きっかけになった誤検知と同じものです。

ここで lint の設定を緩めて通すのは嫌でした。誤検知を避けるためにルールを消すと、何のために lint を入れたのか分からなくなります。そこで、そのルールの判定だけをベンチで 1 位だった [Decider V1.1 27B](https://openrouter.ai/perplexity/pplx-decider-v1.1-27b) に切り替えました。Decider は違反例を違反と判定し、既存の 95 ファイルはすべて違反なしと判定しました。

「無料モデルで誤検知が増えた」という体感から始めて、ベンチでそれを数字にし、その数字で道具を選び直す、というところまで一周できたので、作ってよかったなと思っています。

また、自然文で書いたルールを decision model に判定させる [Oxlint](https://oxc.rs/docs/guide/usage/linter.html) プラグイン([oxlint-plugin-decision](https://github.com/masseater/oxlint-plugin-decision))も作っている最中です。

## まとめ

- 作ったきっかけは、無料の decision model に lint をさせたら誤検知が増え、日本語で測ったベンチが見つからなかったこと
- 測りたかったのは「日本語で書いたルールに照らして判定できるか」で、基準として JNLI を、用途に近いものとして自作の業務ルール判定を置いた
- 件数、タスクの作り方、正解の付け方、採点のルールは、どれも最初の見立てが外れて途中で変えた。それっぽい数字が出ても、何を測っているのかは疑った方がいい
- 自分で考えるより、先行する decision model ベンチの判断に乗った方がだいたい正しかった
- 業務ルール判定の正解は Opus 5.5 との一致率でしかなく、個人の実験として見てほしい
- ベンチの結果は、自分の lint のモデル選びにそのまま使えた
