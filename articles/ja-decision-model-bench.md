## はじめに

最近、選択・二値・スコアだけを返す「decision model」が増えてきました。Jev、Liquid AI の d1、Perplexity の Decider など、文章は生成せず「どれを選ぶか」「はい / いいえの確率」だけを返すモデルです。分類やルーティング、LLM-as-a-judge の代わりに安く速く使えるのが売りです。

decision model 向けのベンチマークとしては Jev Decision Index などがあるのですが、日本語のタスクがありません。日本語で使ったらどうなるのか気になったので、勉強がてらお試しで日本語のベンチマークを作ってみました。

https://mst-ja-decision-bench.masseater.dev

https://github.com/masseater/mst-ja-decision-bench

あくまで勉強目的なので、厳密さよりも「一通り回して結果を眺める」ことを優先しています。結果は話半分で見てください。

## 何を測ったか

タスクは 2 つです。性質がまったく違うので、ページも表もタスクごとに分けています。

| タスク | 形式 | 件数 | 正解 | 採点 |
| --- | --- | ---: | --- | --- |
| [JNLI 含意関係](https://mst-ja-decision-bench.masseater.dev/tasks/jnli) | 3 択 | 2,434 | 人手ラベル | macro-F1 |
| [業務ルール判定](https://mst-ja-decision-bench.masseater.dev/tasks/rules) | 二値 | 500 | Opus 5.5 | balanced accuracy + 対の正解率 |

### JNLI 含意関係

JGLUE の JNLI v1.3 の valid 2,434 件をすべて使いました。2 文の関係を「含意・矛盾・中立」の 3 択で答えさせます。正解は人が付けたラベルです。

最初は 200 件で始めたのですが、正解率 70% 付近だと 95% 信頼区間が ±6 ポイントほどあってモデルの差が見分けられなかったので、全件に増やしました。

### 業務ルール判定

日本語で decision model を使うなら、社内規程に照らして「この申請は OK か」を判定させるような使い方がありそうだと思い、自作しました。

- 架空の会社 25 社分の社内規程(各 8〜12 条、目的・定義・例外・他条の参照を含む)を Claude Opus 5.5 で生成
- 各規程に対して事例の対を 10 組作り、合計 500 件
- 対は [DecideBench](https://github.com/choyiny/decidebench) に倣った最小差分ペアで、ほぼ同じ 2 つの事例の 1 か所(金額、日付、役職、手続きの順序、例外の条件)だけを変えて答えを逆にしている
- 判定するモデルには規程全体と事例を渡して「適合しているか」を二値で答えさせる

対の両方に正解した割合を「対の正解率」として出しています。話題語に反応しているだけだと片方しか当たらないので、条文をちゃんと読めているかが見えます。

正解ラベルは Opus 5.5(effort high)を `claude -p` の構造化出力で 3 回独立に呼んで付け、3 回一致しなかったものや、作るときに意図した答えと多数決が食い違ったものは hard として別集計にしました。ラベル付けの費用は API 換算で 31.19 USD ですが、サブスクリプション経由なので実際の請求はありません。

## 採点方法

採点と見せ方は、既存の decision model ベンチに寄せました。

| ベンチ | 取り入れた点 |
| --- | --- |
| [Jev Decision Index](https://huggingface.co/spaces/multimodalart/jev-decision-index) | 未対応・エラーは 0 点で分母に入れる、全モデル同じ問題文、NLI は macro-F1 |
| [S1MB](https://github.com/hotchpotch/S1MB) | chance 補正した skill、二値は balanced accuracy |
| [DecideBench](https://github.com/choyiny/decidebench) | 最小差分ペアと対の正解率、skill と速度の散布図 |
| [JevBench](https://github.com/fstandhartinger/jevbench) | p50・p95 レイテンシ、ECE と Brier |
| [Arize の比較](https://arize.com/blog/decision-model-benchmark/) | 較正誤差を別に示す |
| [AIM-Decision](https://aimultiple.com/system-one) | 費用と速度は指数に混ぜず別の軸で示す |

- skill は `(raw - chance) / (1 - chance)` で、ランダムに答えたときを 0 にした値です
- 答えられた割合は coverage として別に表示します(今回は全モデル 100% でした)
- 確率から ECE と Brier を出し、確信度と実際の正解率のグラフ(キャリブレーション曲線)も描いています
- skill には 95% 信頼区間を付けています

Choice(選択式)に対応したモデルは 1 リクエストで選択肢ごとの確率を返してくれます。一方で span-01 系のように Noul(はい / いいえ)しか受け付けないモデルには、選択肢ごとの Noul を 1 リクエストにまとめて送り、確率が最大のものを答えにしました。この方法はどの既存ベンチにも書かれていなかった独自のやり方なので、結果では `*` を付けて区別しています。

## 実装

モデルの呼び出しは当面 OpenRouter に一本化して、`@openrouter/sdk` の `systemOne.create` を使っています。ただしモデル id は `openrouter/typesafe/jev-1.13` のように provider を含む形にして、他のプロバイダを後から足せる構造にしました。decision model は OpenRouter 以外にもたくさんあり、今後も増えそうなので、モデルが数十になっても表やグラフが破綻しないことを意識しています(ソート可能な表、上位 10 件表示と「すべて表示」、モデル名での絞り込みなど)。

応答は Effect の `PersistedCache` で 1 件 1 ファイルにキャッシュしていて、再実行しても成功した判定は呼び直しません。ダッシュボードは shadcn/ui の Table と Chart で作り、Cloudflare に置いています。

### span-01 系はほぼランダム

span-01 と span-01 lite は両タスクとも skill 11〜12 で最下位でした。業務ルール判定の対の正解率は 13.8% で、片方だけ当たって片方は外す、つまり条文をほとんど読めていない状態です。

キャリブレーション曲線を見ると、確信度が上がっても正解率はほとんど上がらず、すべての点が対角線より下にあります。自信満々で外しているということです。

![span-01 lite の業務ルール判定のキャリブレーション曲線](/images/ja-decision-model-bench/rules-span-01-lite-calibration.png)

さらに、有料の span-01 と無料の span-01 lite は全 2,934 問で答えも確率も完全に一致しました。少なくとも OpenRouter 経由で日本語を投げた範囲では、同じものが返ってきているように見えます。

## やってみて分かったこと・ハマったところ

- **OpenRouter の `:free` モデルはデータポリシーで弾かれることがある**。mercury-decide:free はアカウントのデータポリシー設定で拒否されたので、有料版を使いました。有料版でも全件で $0.0167 なので誤差です。
- **Clef 系は入力の先頭約 2,000 トークンしか読まない**。規程全体を渡すタスクなので、規程は 1,500 字以内に収めました。
- **否定形の問いは避ける**。Arize の比較で否定形の問いが判定の逆転を招いていたので、問いは「適合しているか」の肯定形に揃えました。
- **LLM に 3 回ラベルを付けさせても意外と割れない**。最初の版では Opus 5.5 の票が割れた問題が 500 件中 1 件しかなく、hard の仕組みが機能していませんでした。そこで「作るときに意図した答えと多数決が食い違う」問題も hard に入れることにしました。
- **見積は実測トークン数から出す**。新しいモデルを回す前に、実測済みモデルのトークン数と単価から見積を出していました。新規 14 モデルで見積 $1.74 に対して実費 $0.96 と、安い側に外れたので安心して回せました。
- **キャッシュは偉い**。応答を 1 件 1 ファイルでキャッシュしているので、途中で落ちても続きから回せます。ただ、キャッシュは 6 万ファイルを超えたので、リポジトリに入れるには少し重くなってきました。
- **decision model 自体を lint にも使ってみた**。jev-lint という decision model でコード規約を判定するツールを CI に入れているのですが、span-01 lite が純粋関数を「UI 状態の扱いの規約違反」と誤検知したので、今回 1 位だった Decider に判定を切り替えました。ベンチの結果と体感が一致していて面白かったです。

## おわりに

勉強目的のお試しですが、日本語で 16 モデルを一通り並べてみると、JNLI のような素直な分類では上位がほぼ横並びなのに対し、規程を読ませる業務寄りのタスクではかなり差が付くことが分かりました。また、全モデル合わせても 1 回あたり約 $1 で回せるので、手元のユースケースに近いタスクを作って測ってみるのは割とおすすめです。

なお、業務ルール判定の正解は Opus 5.5 が付けたものなので、スコアは「Opus 5.5 との一致率」であって本当の正しさではありません。その点はご注意ください。

今後は OpenRouter 以外のプロバイダの decision model も足していきたいと思っています。
