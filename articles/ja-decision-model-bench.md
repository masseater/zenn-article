## はじめに

最近、選択・二値・スコアだけを返す「decision model」が増えてきました。Jev、Liquid AI の d1、Perplexity の Decider など、文章は生成せず「どれを選ぶか」「はい / いいえの確率」だけを返すモデルです。

使ってみたいなと思って既存のベンチマークを眺めていたのですが、Jev Decision Index などには日本語のタスクがありません。日本語で使ったらどうなるのか分からなかったので、勉強がてら自分で作ってみることにしました。

結果の公開サイトはこちらです。

https://mst-ja-decision-bench.masseater.dev

コードはこちらです。

https://github.com/masseater/mst-ja-decision-bench

結果はサイトを見てもらうとして、この記事では作っている途中でつまずいたことや、やり直したこと、意外だったことを書きます。ベンチマークを作るのは初めてで、厳密さよりもとにかく一通り回すことを優先しました。

## 最初は 200 件で十分だと思っていた

タスクの 1 つ目には、JGLUE の JNLI(2 文の関係を「含意・矛盾・中立」の 3 択で答える)を選びました。人が付けた正解があるので、正解ラベルを用意する手間がかかりません。

最初は「お試しだし 200 件くらいでいいか」と思って 200 件で回しました。ところが結果に 95% 信頼区間を付けてみると、正解率 70% 付近で ±6 ポイントくらいの幅があって、モデル同士の差がほとんど区間の中に埋もれてしまいました。順位表っぽいものは出るのに、その順位にはほぼ意味がない状態です。

JNLI は人手ラベルがあって件数を増やしても追加費用がかからないので、valid の 2,434 件を全部使うことにしました。区間を付けていなかったら、200 件の順位をそのまま信じていたと思います。

## 自作タスクは一度作り直した

2 つ目のタスクは、日本語で decision model を業務に使うならこういう使い方をしそう、という想定で「社内規程に照らしてこの事例は適合しているか」を判定させる業務ルール判定にしました。データは Claude Opus 5.5 で架空の会社の規程と事例を生成しています。

最初の版は「条文 1 つと事例 1 つ」を渡す形でした。一応それっぽい結果は出たのですが、よく見ると「第 n 条」は飾りで、条文を読まなくても事例の話題語だけで当てられてしまう問題ばかりでした。これでは日本語の規程を読めているかは測れません。

そこで作り直しました。

- 1 テーマにつき 8〜12 条の規程を作り、毎回その規程全体を読ませる
- 事例は 2 つ以上の条を組み合わせないと判断できないものにする
- [DecideBench](https://github.com/choyiny/decidebench) を真似て、ほぼ同じ 2 つの事例の 1 か所(金額、日付、役職など)だけを変えて答えを逆にした「対」にする
- 対の両方に正解した割合を「対の正解率」として出す

作り直す前後で同じモデル(span-01 lite)を測ってみたところ、skill は 40.9 から 12.2 に落ち、対の正解率は 13.8% でした。作り直す前の数字は、規程を読む力ではなく話題語への反応を測っていたということです。自作タスクは、それっぽい数字が出ても何を測っているのかを疑った方がいいなと思いました。

ほかにも、Arize の比較記事で否定形の問いが判定の逆転を招いていたので問いを肯定形に揃えたり、Cloudflare の Clef 系が入力の先頭約 2,000 トークンしか読まないと分かって規程を 1,500 字以内に収めたりと、細かい調整をしています。

## LLM に 3 回聞いても割れない

業務ルール判定の正解は Opus 5.5 に付けてもらっています。1 問ごとに `claude -p` を構造化出力で 3 回独立に呼んで、3 回とも一致したものだけを採点に使い、割れたものは「hard」として別にするつもりでした。

ところが実際に回してみると、500 件中で票が割れたのは 1 件だけでした。同じ問題を何度聞いても、LLM はだいたい同じ答えを返してきます。3 回聞けば迷う問題を見つけられるだろうと思っていたので、これは意外でした。

結局、「作るときに意図した答えと、3 回の多数決が食い違う問題」も hard に入れることにしました。ちなみに JNLI で Opus 5.5 のラベルと人の正解を比べると一致率は 91.5% で、LLM のラベルも 1 割弱は人とずれます。業務ルール判定のスコアは「Opus 5.5 との一致率」でしかない、というのは README とサイトにも書いています。

## 自己流の採点をやめて既存ベンチに寄せた

最初は正解率を出していただけだったのですが、途中で既存の decision model ベンチ(Jev Decision Index、S1MB、DecideBench、JevBench、Arize の比較、AIM-Decision)をちゃんと読みました。読んでみると、自分が気にしていなかった点がいくつもありました。

- 答えられなかった問題を分母から外すと、難しい問題だけ落とすモデルが得をする。なので未対応やエラーは 0 点で分母に入れ、答えた割合は coverage として別に出す
- 3 択と二値では偶然当たる確率が違うので、生の正解率のままだとタスク間で比べられない。ランダムに答えたときを 0 にした skill に揃える
- NLI は正解率ではなく macro-F1 で採点する
- 費用と速度はスコアに混ぜず、別の軸で見せる

どれも言われてみればその通りなのですが、自分だけでは思いつきませんでした。自分で考えるより、先にやっている人の判断に乗っかった方がだいたい正しいです。

一方で、どのベンチにも書かれていなかったこともありました。span-01 系のように「はい / いいえ」しか受け付けないモデルに 3 択をどう解かせるかです。ルール通り 0 点にすると JNLI では何も測れないので、選択肢ごとに「次の答えは正しいですか: 含意」という問いを作って 1 リクエストにまとめて送り、「はい」の確率が最大のものを答えにしました。独自のやり方なので、結果では `*` を付けて区別しています。

## 回してみて意外だったこと

16 モデルを一通り回して、いちばん意外だったのは次の 3 つです。

**タスクによって順位がかなり入れ替わる。** JNLI では上位がほぼ横並びなのに、規程を読ませる業務ルール判定では差が大きく開きました。JNLI では中位以下だった Solar Decide が業務ルールでは 2 位に来たりもします。1 つのタスクの順位で「このモデルが強い」とは言えないなと実感しました。その Solar Decide は業務ルール判定で 1 判定の p50 が約 18.7 秒と、他が 200〜500 ms なのに比べて桁違いに遅く、速度を別に見せておいてよかったと思いました。

**確信度が当てにならないモデルがある。** 確信度と実際の正解率のグラフを描いてみると、確信度が上がっても正解率がほとんど上がらないモデルがありました。確率を返してくれるからといって、そのまま閾値に使うのは危ないです。

**有料版と無料版が同じものを返していた。** 有料の span-01 と無料の span-01 lite は、全 2,934 問で答えも確率も完全に一致しました。並べて測らなければ気づかなかったと思います。

## お金の話

decision model は安いです。OpenRouter 上の新規 14 モデルを全件回したとき、事前の見積は $1.74 で、実費は約 $0.96 でした。全モデル合わせても 1 周 1 ドル前後です。

ただ、作業は Claude Code に任せて回していたので、何かの拍子に呼びすぎるのが怖く、OpenRouter の API キーには月の利用上限をかけました。新しいモデルを足すときも、先に実測済みモデルのトークン数と単価から見積を出してもらい、自分が OK してから回すようにしています。推測の見積で回すとどこかで痛い目を見そうだったので、このルールは最初に決めてよかったです。

ラベル付けに使った Opus 5.5 は API 換算だと 30 ドルを超えますが、サブスクリプション経由の `claude -p` で動かしたので実際の請求はありません。地味にハマったのは、OpenRouter の `:free` 付きモデルがアカウントのデータポリシー設定で拒否されたことです。有料版でも数セントだったので有料版を使いました。

## ベンチの結果が自分の CI で役に立った

最後に、ちょっと面白かった話です。このリポジトリでは、jev-lint という decision model でコード規約を判定するツールを CI に入れていて、最初は無料の span-01 lite で判定していました。

あるとき、UI 状態を持たない純粋関数が「UI 状態の扱いの規約違反」と判定されて CI が落ちました。span-01 lite に違反例と違反でない例を判定させてみると、ほとんど区別できていません。ちょうど自分のベンチで span-01 lite が最下位だったのと同じ傾向です。

lint の設定を緩めて通すのは嫌だったので、そのルールの判定だけをベンチで 1 位だった Decider に切り替えたところ、違反例は正しく違反、既存のファイルは全部違反なしと判定されました。自分で作ったベンチの結果をそのまま自分の道具選びに使えたのは、作ってよかったと思えた瞬間でした。

## おわりに

勉強目的のお試しでしたが、一番の学びは「データの作り方と採点のルールで、数字の意味がまるで変わる」ということでした。200 件の順位、話題語で当たる自作タスク、分母から外れる失敗など、どれも最初はそれっぽい数字が出ていて、気づかなければそのまま信じていたと思います。

decision model は 1 判定あたりの費用が非常に安いので、手元のユースケースに近いタスクを作って測ってみるのはおすすめです。今後は OpenRouter 以外のプロバイダのモデルも足していきたいと思っています。
